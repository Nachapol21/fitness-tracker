# แอปฟิตเนส (fitness-tracker)

เว็บแอปบนมือถือ (PWA) ภาษาไทย ไว้**จดการฝึกเวท จดการกิน และวิเคราะห์ความคืบหน้า**
ทำจาก HTML + CSS + JavaScript ล้วน ไม่มี framework ไม่มีขั้น build ไม่ต้อง `npm install` ใช้ออฟไลน์ได้ในยิม

ข้อมูลทั้งหมดเก็บใน IndexedDB ของเบราว์เซอร์ในเครื่องที่ใช้ ถ้าไม่ล็อกอินก็ไม่ได้ส่งไปที่ไหน · ถ้าอยากใช้หลายเครื่อง (iPhone + คอม) ล็อกอินเพื่อ**ซิงก์ผ่าน Supabase** ได้ (ดูหัวข้อ "ซิงก์ระหว่างเครื่อง") แอปยังใช้ได้ครบโดยไม่ล็อกอิน

## ทำอะไรได้

| แท็บ | ทำอะไรได้ |
|---|---|
| วันนี้ | **การ์ดเกม (coin · ไฟ 🔥 · ตัวคูณ · ร้าน/ประวัติ)** · สรุปแคลอรี่/โปรตีน/คาร์บ/ไขมันของวันเทียบเป้า · เริ่มฝึก · จดน้ำหนัก รอบเอว ก้าวเดิน หมายเหตุ · น้ำดื่ม · เปลี่ยนวันได้ |
| ฝึก | จดเซ็ต (น้ำหนัก × ครั้ง, RIR, วอร์มอัพ) · ปุ่ม **"เหมือนครั้งก่อน"** · คาร์ดิโอ (เดินชัน/วิ่ง/ปั่น) พร้อมประมาณ kcal · คลังท่าที่เพิ่ม/แก้เองได้และระบุเครื่องได้ · คำแนะนำเพิ่มน้ำหนักและเตือนท่าที่ตัวเลขไม่ขึ้นในหน้าจด |
| กิน | คลังอาหารตั้งต้น 35 รายการ (เมนูไทย/เซเว่น เป็น**ค่าประมาณ** แก้/เพิ่มเองได้) · รายการโปรดแตะครั้งเดียวเพิ่ม · มื้อ · จำนวนที่ · Quick add (kcal + โปรตีน) · น้ำดื่ม |
| วิเคราะห์ | รายสัปดาห์ (น้ำหนักเฉลี่ย, kcal/โปรตีนเฉลี่ย, จำนวนครั้งที่ฝึก, PR, สิ่งที่ควรปรับ) · น้ำหนักเฉลี่ย 7 วัน + แนวโน้ม + คำเตือน · kcal/โปรตีนเทียบเป้า · ประมาณ TDEE จริง · กราฟแต่ละท่า (เซ็ตที่ดีที่สุด / 1RM Epley / ปริมาณรวม) · เซ็ตต่อกลุ่มกล้าม · สัดส่วน ดัน:ดึง:ขา · ความสม่ำเสมอเทียบเป้า · ท่าที่พร้อมเพิ่มน้ำหนัก |
| ตั้งค่า | โปรไฟล์ + คำนวณ BMR/TDEE (Mifflin-St Jeor) และเป้า kcal/โปรตีน/ไขมัน/คาร์บ · **ตั้งค่าเกม coin** · ธีม สว่าง/มืด/ตามเครื่อง · **บัญชีและซิงก์** · ส่งออก/นำเข้า · สถานะที่เก็บข้อมูล · วิธีติดตั้งบน iPhone |

กติกาของตัวเลขวิเคราะห์ (ทั้งหมดอยู่ใน `js/analytics.js`):

- **น้ำหนัก**: ค่าเฉลี่ย 7 วัน, แนวโน้มจาก 21 วันล่าสุด; เตือนถ้า ≥ 2 สัปดาห์น้ำหนักไม่ลด หรือลดเร็วเกิน 1 กก./สัปดาห์; ถ้าชั่งน้อยเกินไปจะบอกว่าข้อมูลยังไม่พอ
- **ประมาณ TDEE จริง** = แคลอรี่ที่กินเฉลี่ย − (น้ำหนักที่เปลี่ยนต่อวัน × 7,700) ต้องจดอาหารครบ ≥ 14 วัน (วันละ ≥ 800 kcal จึงนับว่าจดครบ) และชั่งน้ำหนัก ≥ 4 ครั้งห่างกัน ≥ 12 วัน ถ้าไม่ถึงจะขึ้น **"ข้อมูลยังไม่พอ"** พร้อมบอกว่าตอนนี้มีเท่าไร
- **แนะนำเพิ่มน้ำหนัก**: ครั้งล่าสุดทำถึงเลขบนของช่วงครั้งทุกเซ็ตทำงาน → ท่าช่วงบน +1–2.5 กก., ท่าขา +2.5–5 กก.
- **ตัวเลขไม่ขึ้น 3 ครั้งติด**: 3 ครั้งล่าสุดไม่มีครั้งไหนทำลายสถิติ (1RM ประมาณ) ของครั้งก่อนหน้า และไม่ได้ไต่ขึ้นเรื่อยๆ (ต้องมีประวัติ ≥ 4 ครั้ง)
- เซ็ตวอร์มอัพไม่นับในสถิติทุกอย่าง · สัปดาห์เริ่มวันจันทร์

> แอปนี้ให้ข้อมูลเชิงสถิติจากที่ผู้ใช้จดเท่านั้น ไม่ใช่คำแนะนำทางการแพทย์ ค่าอาหารและ kcal คาร์ดิโอเป็นค่าประมาณ

## เกม coin และ streak

ทำตามแผน (กินตามเป้า ฝึก ชั่งน้ำหนัก ฯลฯ) แล้วได้ **coin** เอาไปแลกรางวัลในร้าน (ชานม ชาบู ดูหนัง หรืออะไรก็ได้ที่ตั้งเอง) และมี **ไฟ 🔥** นับวันที่ทำตามแผนติดกัน ไม่ต้องมีแท็บใหม่: การ์ด "🎮 เกม" อยู่ในหน้า **วันนี้** มีปุ่มไป **ร้านรางวัล** (`#/shop`) และ **ประวัติ coin** (`#/coins`) · ตัวเลขทุกตัวด้านล่างเป็นค่าเริ่มต้น แก้ได้ที่ ตั้งค่า → "เกม coin และ streak"

**วิธีได้ coin** (ทั้งหมดอยู่ใน `js/game.js`)

| ทำอะไร | coin | เงื่อนไข |
|---|---|---|
| ฝึกครบ 1 ครั้ง | +10 | ≥ 4 ท่า หรือ ≥ 8 เซ็ตทำงาน (ไม่นับวอร์มอัพ) · วันละไม่เกิน 1 ครั้ง |
| คาร์ดิโอ | +3 | รวม ≥ 15 นาทีในวัน |
| สถิติใหม่ (PR) | +5 ต่อท่า | นิยามเดียวกับหน้าวิเคราะห์ (1RM ประมาณใหม่ ต้องเคยเล่นท่านั้นมาก่อน) · ไม่เกิน 15/วัน |
| แคลอรี่ในช่วงเป้า | +5 | เป้า ± "ยอมรับได้" ในโปรไฟล์ (`kcal_tolerance` ตัวเดียวกับหน้าวิเคราะห์ เช่น 2,000 ± 100 = 1,900–2,100) และจดอย่างน้อย 2 มื้อที่ต่างกัน (quick add นับเป็นมื้อ) · เข้าเมื่อวันนั้นจบ · ตั้งค่าเกมใส่ช่วงของเกมเองได้ (ว่าง = ตามโปรไฟล์) |
| โปรตีนถึงขั้นต่ำ | +5 | ≥ โปรตีนต่ำสุดในโปรไฟล์ |
| ก้าวถึงเป้า | +2 | ≥ เป้าก้าวในโปรไฟล์ |
| ชั่งน้ำหนัก | +1 | |
| ฝึกครบ 4 ครั้ง/สัปดาห์ | +30 | ลงที่วันฝึกครั้งที่ 4 (จันทร์–อาทิตย์) ไม่คูณตัวคูณ |

**ไฟรายวัน** = วันที่แคลอรี่อยู่ในช่วง **และ** (มีการฝึก หรือเป็นวันพัก) · วันที่ไม่ได้ฝึกนับเป็นวันพักได้ไม่เกิน 3 วัน/สัปดาห์ (จ–อา) ถ้าเกินวันนั้นนับว่าพลาด · วันที่ไม่ได้จดอาหารไม่กินโควตาวันพัก · วัน "ได้รับอนุญาต" ไม่ถูกตัดด้วยโควตาวันพักและไม่กินโควตานั้น · วันนี้ยังไม่จบ จึงไม่มีวันนี้ที่ "พลาด" · หน้าวันนี้บอกคำใบ้ "วันฝึก/วันพักตามแผน" ตามวันฝึกที่ตั้งไว้
**ตัวคูณ** ใช้ความยาวไฟ ณ สิ้นวันก่อนหน้า: 7 วัน ×1.2 · 14 วัน ×1.5 · 30 วัน ×2 · ปัดเศษลงต่อรายการ
**ไฟรายสัปดาห์** = จำนวนสัปดาห์ที่จบแล้วติดกันที่ฝึกครบ 4 ครั้ง (รวมสัปดาห์นี้ถ้าครบแล้ว)
**วันได้รับอนุญาต** = วันที่แลกรางวัลของกิน (kcal > 0) ไฟไม่ดับแม้แคลอรี่เกินช่วง (สัปดาห์ละ 1 วัน) วันนั้นไม่ได้ coin แคลอรี่
**ไฟสำรอง 🧊** ซื้อในร้าน 30 coin ถือได้ทีละ 1 อัน ถูกใช้เองกับวันแรกที่พลาดหลังซื้อ (ไม่ใช้กับวันนี้) · ไฟดับแล้ว coin ไม่หาย แค่ตัวคูณกลับไป ×1
**ร้าน** เพิ่ม/แก้/ลบรางวัลได้ (ลบแบบ soft delete) ปุ่มแลกเป็นสีเทาพร้อมเหตุผลถ้า coin ไม่พอ/ติด cooldown · ก่อนแลกมีหน้ายืนยัน ถ้าเป็นของกินถามว่าจะเพิ่มลงบันทึกการกินวันนี้ไหม (kcal ประมาณ แก้ได้) · ≥ 800 kcal ขึ้นคำแนะนำให้ลด 100–150 kcal/วันในวันอื่นของสัปดาห์ (แค่แนะนำ) · "ยกเลิกการแลก" ได้ภายในวันเดียวกัน (คืน coin และเอารายการที่ลงบันทึกการกินออก) · ถ้ายอดติดลบ (เพราะแก้ข้อมูลย้อนหลัง) จะแสดงตามจริงแต่แลกเพิ่มไม่ได้
**ฉลอง** แอนิเมชัน CSS เบาๆ ตอนไฟถึง 7/14/30 วัน ครั้งเดียวต่อเหตุการณ์ (จำใน `meta` ของเครื่องนั้น ไม่ซิงก์ จึงแต่ละเครื่องฉลองของตัวเอง) และปิดอัตโนมัติถ้าเครื่องตั้ง "ลดการเคลื่อนไหว"

**ทำไม coin คำนวณจาก log ทุกครั้ง (ไม่เก็บเป็นรายการ +coin)**
ถ้าเก็บรายการ +coin สองเครื่องที่ซิงก์กันจะให้ coin ซ้ำกันได้ และแก้ข้อมูลย้อนหลังแล้วจะได้ coin ซ้ำอีก การคำนวณจากข้อมูลที่จดจึงกันทั้งสองอย่าง: ยอด = coin ที่คำนวณได้จาก log − การแลก (`redemptions`) เครื่องไหนซิงก์ครบแล้วยอดเท่ากันเสมอ · ผลข้างเคียงที่ควรรู้: แก้/ลบข้อมูลย้อนหลังแล้วยอดเปลี่ยนตาม (ติดลบได้) และ **เปลี่ยนค่าตั้งค่าเกมแล้ว coin ในอดีตคำนวณใหม่ทั้งหมดด้วยค่าใหม่**

**กฎวันที่ของ coin**
- กิจกรรมที่ `created_at` (แปลงเป็นวันตามเวลาไทย UTC+7) ช้ากว่า `date` เกิน 2 วัน (ตั้งค่าได้) ไม่ได้ coin แต่ยังนับในไฟและสถิติ · กิจกรรมที่ **จดล่วงหน้า** (`created_at` เป็นวันก่อน `date`) ก็ไม่ได้ coin เช่นกัน
- **วันเริ่มนับ coin (`start_date`)**: coin นับเฉพาะวันที่ ≥ `start_date` ซึ่งแอปตั้งเป็น "วันนี้ตามเวลาไทย" ตอนสร้างการตั้งค่าเกมครั้งแรก (แก้ได้ในตั้งค่าเกม ล้างช่อง = นับทุกวัน) ส่วนไฟนับจากประวัติทั้งหมดเหมือนเดิม — เพราะข้อมูลที่นำเข้าจาก log.md มี `created_at` เป็นวันของมันเอง ดูเหมือนจดตรงเวลา ถ้าไม่มีวันเริ่มจะได้ coin ย้อนหลังก้อนใหญ่ · ถ้าล็อกอินซิงก์อยู่ แอปรอซิงก์ครั้งแรกเสร็จก่อนค่อยสร้าง (กันทับค่าจากเครื่องอื่น) · ข้อจำกัด: สองเครื่องที่ยังไม่เคยเห็นของกันสร้างพร้อมกัน ฝั่งที่ใหม่กว่าชนะ (LWW) `start_date` อาจต่างกันไม่กี่วัน แก้ได้ในตั้งค่า
- **การแก้ค่าของ log ที่จดตรงเวลาทีหลัง (ไม่ใช่การเพิ่มรายการใหม่) ยังได้ coin ตามค่าใหม่ — ตั้งใจไม่ป้องกัน (WONTFIX)**: ดูแค่ `created_at` เพราะเป็นมิตรกับคนที่จดผิดแล้วแก้ทีหลัง ป้องกันการเติมรายการใหม่ย้อนหลังได้แล้ว (รายการใหม่มี `created_at` ใหม่) และเกมนี้เป็นของส่วนตัว ไม่ใช่การแข่งขัน

**ข้อมูลที่เก็บ/ซิงก์/ส่งออก** (3 ตาราง ผ่าน `db.js` เหมือนตารางอื่น ซิงก์ผ่าน `sync_records` ได้เลยไม่ต้องแก้ฐานข้อมูล):

| ตาราง | ฟิลด์ |
|---|---|
| `game_settings` | เรคคอร์ดเดียว id คงที่ `00000000-0000-4000-8000-000000000002` · ค่าทุกตัวใน `DEFAULT_GAME_SETTINGS` (`js/constants.js`) |
| `rewards` | name, emoji, price, kcal, cooldown_days, active · รางวัลตั้งต้น 5 อัน id คงที่ (`seedRewards`) |
| `redemptions` | date, kind (`reward`/`freeze`), reward_id, name, emoji, price (snapshot ตอนแลก), coins, kcal, food_log_id |

`coin_transactions` เป็นมุมมองที่คำนวณขึ้น (`coinTransactions()` รวมที่ได้กับที่ใช้) ไม่ได้เก็บจริง · ไฟล์สำรอง JSON เป็น `version: 2` (แอปรุ่นเก่าจะปฏิเสธแทนที่จะทิ้งข้อมูลเกมเงียบๆ ส่วนไฟล์รุ่นก่อนเกมนำเข้าได้ปกติ และนำเข้าแบบ "แทนที่" จะลบเฉพาะตารางที่มีอยู่ในไฟล์ — ข้อมูลเกมไม่ถูกลบเมื่อใช้ไฟล์รุ่นเก่า)

**แอปอัปเดตแล้วบางเครื่องยังเป็นรุ่นเก่า (ซิงก์)**: รุ่นก่อนเกมข้ามแถวของ collection ที่ไม่รู้จักแล้วเลื่อน cursor ไป รุ่นนี้จึงเก็บ `sync_tables_version` ใน meta (ไม่ซิงก์) ถ้าน้อยกว่าปัจจุบันจะดึงใหม่จากต้นหนึ่งครั้งตอนซิงก์ครั้งแรก (การรวมเป็น LWW ปลอดภัย) และต่อไปถ้าเจอแถวของ collection ที่ไม่รู้จัก ตัว cursor จะไม่เลื่อนผ่านแถวนั้น · ถ้าที่เก็บข้อมูลเปิดค้างอยู่ในแท็บเก่า แอปจะขึ้นหน้า "ปิดหน้าต่างแอปเก่าก่อน" (แท็บเก่าที่เป็นรุ่นนี้ปิดตัวเองและโหลดใหม่ให้)

หมายเหตุ: ไฟลำดับวันพักใช้ "จำนวนวันที่ไม่ได้ฝึก" ตามลำดับเวลาในสัปดาห์ (วันฝึกตามแผนในตั้งค่าใช้แสดงคำใบ้เท่านั้น ไม่ตัดสินพลาด) เพื่อให้สลับวันฝึกได้โดยไฟไม่ดับ · วันที่ใช้เทียบเป็นวันของเครื่อง ส่วน `created_at` แปลงเป็นเวลาไทย

## รันบนเครื่อง

ต้องเปิดผ่านเว็บเซิร์ฟเวอร์ (เปิดไฟล์ `index.html` ตรงๆ ไม่ได้ เพราะใช้ ES modules และ service worker)

```bash
cd projects/fitness-tracker
python -m http.server 8080 --bind 127.0.0.1
# เปิด http://localhost:8080/
```

- ใช้ `--bind 127.0.0.1` เพื่อไม่ให้เครื่องอื่นในเครือข่ายเห็นไฟล์ (โฟลเดอร์ `private/` จะถูกเสิร์ฟด้วยเมื่อรันแบบนี้)
- ทดสอบสูตรคำนวณ: `node --test` (ใช้ Node 20+ ไม่ต้องติดตั้งอะไร)

## โครงข้อมูลสำหรับซิงก์

ทุกเรคคอร์ดในทุกตารางมี 4 ฟิลด์นี้เสมอ:

| ฟิลด์ | ความหมาย |
|---|---|
| `id` | UUID (`crypto.randomUUID`) |
| `created_at` | เวลาสร้าง ISO-8601 UTC |
| `updated_at` | เวลาแก้ล่าสุด ISO-8601 UTC (`db.update` ตั้งให้ทุกครั้ง) |
| `deleted` | `true` = ลบแบบ soft delete (เรคคอร์ดยังอยู่ ไม่ลบจริง) |

ตาราง (object store) และฟิลด์เฉพาะ:

| ตาราง | ฟิลด์ |
|---|---|
| `profile` | เรคคอร์ดเดียว id คงที่ `00000000-0000-4000-8000-000000000001` · sex, age, height_cm, activity, goal, rate_kg_week, calc_weight_kg, kcal, kcal_tolerance, protein_min, protein_max, fat, carb, sessions_per_week, step_goal, water_goal_ml |
| `body_logs` | date, weight_kg, waist_cm, steps, note (1 เรคคอร์ด/วัน) |
| `exercises` | name, muscle, category (ดัน/ดึง/ขา/core), equipment, machine, rep_min, rep_max, per_side, timed, note |
| `sessions` | date, day_name, start_time, end_time, rpe, note, exercise_ids[] (ลำดับท่าในครั้งนั้น), date_estimated? |
| `sets` | session_id, exercise_id, order, weight_kg, reps, rir, is_warmup, note |
| `cardio` | session_id, date, type, minutes, incline_pct, speed_kmh, distance_km, kcal_est, note |
| `foods` | name, serving, kcal, protein, carb, fat, favorite, estimated |
| `food_logs` | date, meal, food_id, name, serving, qty, kcal, protein, carb, fat, quick (เก็บค่ารวมไว้ในรายการ แก้คลังอาหารภายหลังไม่ทำให้ประวัติเพี้ยน) |
| `water_logs` | date, ml (1 เรคคอร์ดต่อการดื่มหนึ่งครั้ง) |
| `game_settings`, `rewards`, `redemptions` | ดูหัวข้อ "เกม coin และ streak" |
| `templates` | name, items[{exercise_id, name, sets, rep_min, rep_max, per_side, timed}], note (เก็บไว้ ยังไม่มีหน้าจอ) |
| `meta` | ค่าเฉพาะเครื่อง (เวลา export ล่าสุด ฯลฯ) **ไม่ซิงก์ ไม่ export** |

สิ่งที่ออกแบบไว้ให้ต่อซิงก์ได้ง่าย:

- เขียน/อ่านข้อมูลผ่าน `js/db.js` ที่เดียว และมี `db.onChange(fn)` แจ้งทุกครั้งที่เขียน · ทุกครั้งที่เขียนจะจดลงตาราง `dirty` (คิวรอส่ง) ใน transaction เดียวกับตัวข้อมูล
- กฎรวมข้อมูลมีอยู่แล้วใน `db.importData`: id เดียวกัน → ฝั่งที่ `updated_at` ใหม่กว่าชนะ (last-write-wins ต่อเรคคอร์ด) ใช้ตรรกะเดียวกันกับการซิงก์ได้
- ท่า/อาหารตั้งต้นและข้อมูลที่นำเข้ามี id คงที่ (คำนวณจากเนื้อหา) สองเครื่องจึงไม่สร้างรายการซ้ำ
- วันที่ (`date`) เป็นสตริงวันท้องถิ่น `YYYY-MM-DD` ส่วนเวลา `*_at` เป็น UTC
- ข้อควรระวัง: `sessions.exercise_ids` เป็น array ที่เขียนทับทั้งก้อน ถ้าแก้พร้อมกันสองเครื่องจะชนกันระดับเรคคอร์ด · `updated_at` พึ่งนาฬิกาเครื่อง

## ซิงก์ระหว่างเครื่อง

ใช้ Supabase (ฐานข้อมูล Postgres + ระบบล็อกอิน) เป็นตัวกลางเก็บข้อมูลชุดเดียวกันให้ทุกเครื่อง แอปคุยกับ Supabase ด้วย `fetch` ล้วน ไม่ใช้ `supabase-js` และไม่โหลดอะไรจาก CDN

หลักการ: **local-first** — ข้อมูลหลักอยู่ในเครื่องเสมอ จดได้ปกติแม้ออฟไลน์ การซิงก์เป็นแค่การส่งส่วนที่เปลี่ยน/ดึงส่วนที่อีกเครื่องเปลี่ยน ไม่ล็อกอินก็ใช้แอปได้ครบ

### วิธีสมัครและล็อกอิน

1. เปิดแอป → แท็บ **ตั้งค่า** → การ์ด **"บัญชีและซิงก์"**
2. กรอกอีเมลกับรหัสผ่าน (อย่างน้อย 6 ตัว) แล้วกด **"สมัครบัญชีใหม่"**
3. Supabase ส่งอีเมลยืนยันให้ → **ไปกดลิงก์ยืนยันในอีเมลก่อน แล้วค่อยกลับมาล็อกอิน**
4. กลับมาที่การ์ดเดิม กด **"ล็อกอิน"** — แอปจะซิงก์ทันที (ครั้งแรกจะรวมข้อมูลในเครื่องกับบนเซิร์ฟเวอร์ให้ทั้งสองทาง ไม่ทับกันแบบทั้งก้อน)
5. เครื่องอื่น (เช่น คอม) ทำข้อ 4 ด้วยอีเมลเดียวกัน — ไม่ต้องสมัครใหม่

ในการ์ดจะเห็น สถานะ · เวลาซิงก์ล่าสุด · จำนวนรายการที่รอส่ง · จำนวนรายการที่ส่งไม่ได้ (ถ้ามี) · ข้อผิดพลาด (ภาษาไทย) และปุ่ม **"ซิงก์ตอนนี้"** ส่วนหน้า **"วันนี้"** มีจุดสีเล็กๆ ข้างหัวข้อ: เขียว = ซิงก์แล้ว · เหลือง = รอส่ง/ออฟไลน์ · แดง = ซิงก์ไม่สำเร็จ · เทา = ยังไม่ล็อกอิน (แตะเพื่อไปหน้าตั้งค่า)

แอปซิงก์เองเมื่อ: เปิดแอป · กลับมาออนไลน์ · กลับมาเปิดแอป/แท็บ · ไม่กี่วินาที (ประมาณ 5) หลังจดข้อมูลเสร็จ

**ออกจากระบบ** จะถามว่าจะ *เก็บ* หรือ *ล้าง* ข้อมูลในเครื่อง (แอปพยายามส่งของที่ค้างให้เสร็จก่อน ถ้าล้างตอนที่ยังมีของค้างจะเตือน) — จะใช้บัญชีอื่นบนเครื่องเดียวกัน ต้องเลือกล้าง เพราะข้อมูลในเครื่องผูกกับบัญชีเดียว ไม่งั้นข้อมูลสองบัญชีจะปนกัน

### สิ่งที่ผู้ใช้ต้องตั้งเองในหน้าเว็บ Supabase (ทำครั้งเดียว)

1. **Authentication → URL Configuration → Site URL** = ที่อยู่เว็บของแอปบน GitHub Pages (เช่น `https://<ชื่อผู้ใช้>.github.io/<ชื่อ repo>/`) ไม่งั้นลิงก์ในอีเมลยืนยันจะพาไปที่อยู่ผิด
2. **หลังสมัครบัญชีของตัวเองแล้ว ให้ปิด "Allow new users to sign up"** (Authentication → Sign In / Providers) ไม่งั้นใครก็สมัครบัญชีใช้โปรเจกต์นี้ได้ — ข้อมูลแต่ละบัญชีแยกกันด้วย RLS อยู่แล้ว แต่ปิดไว้ปลอดภัยกว่าและกันโควตาเต็ม · ถ้าอยากเพิ่มเครื่อง/ล็อกอินใหม่ **ไม่ต้องเปิดอีก** (ล็อกอินด้วยบัญชีเดิมได้) · ถ้าปิดแล้วลองสมัคร จะขึ้น "ปิดรับสมัครบัญชีใหม่แล้ว"

(ตาราง `sync_records` (PK คือ `user_id, id`), RLS และ trigger ถูกสร้างไว้ที่ Supabase แล้ว ไม่ต้องทำอะไรเพิ่ม)

### ความปลอดภัย

- `js/config.js` มี URL โปรเจกต์ + **publishable key** (`sb_publishable_…`) ซึ่ง Supabase ออกแบบให้อยู่ในโค้ดฝั่งเว็บได้ ใครเห็นก็ทำอะไรไม่ได้ถ้าไม่ล็อกอิน ความปลอดภัยมาจาก **Row Level Security** ที่เซิร์ฟเวอร์: ผู้ล็อกอินอ่าน/เพิ่ม/แก้ได้เฉพาะแถวของตัวเอง ไม่มีสิทธิ์ลบ และไม่ล็อกอินเข้าตารางไม่ได้เลย
- **ห้ามใส่ `service_role` หรือ secret key (`sb_secret_…`) ในโปรเจกต์นี้เด็ดขาด** — เทสต์จะล้มถ้าเจอ
- เก็บเฉพาะ session (access/refresh token) ใน `localStorage` ไม่เก็บรหัสผ่าน · ข้อมูลฟิตเนสบนเซิร์ฟเวอร์ไม่ได้เข้ารหัสแบบ end-to-end (เจ้าของโปรเจกต์ Supabase เห็นได้)
- ถ้าจะปิดซิงก์ทั้งหมด: ตั้ง `url` หรือ `publishableKey` ใน `js/config.js` เป็นสตริงว่าง การ์ดบัญชีจะหายและแอปทำงานในเครื่องล้วน

### การทำงานของ LWW (last-write-wins)

- ทุกเรคคอร์ดมี `updated_at` (เวลา UTC ที่แก้ล่าสุด) **ฉบับที่แก้ทีหลังชนะ ทั้งรายเรคคอร์ด** ไม่ใช่รายฟิลด์: ถ้าสองเครื่องแก้เรคคอร์ดเดียวกันคนละช่อง ฉบับที่ใหม่กว่าจะแทนทั้งเรคคอร์ด (เช่น น้ำหนักของวันเดียวกัน)
- ตอนเขียนในเครื่อง `updated_at` จะมากกว่าค่าเดิมเสมอ (กันนาฬิกาเครื่องเดินช้าแล้วการแก้แพ้ของเก่า) แต่ระหว่างเครื่องต่างกันยังพึ่งนาฬิกาของแต่ละเครื่อง — ตั้งเวลาอัตโนมัติไว้ทุกเครื่อง
- **ส่ง (push):** ส่งเฉพาะรายการที่ยังไม่เคยส่ง เป็นชุดละไม่เกิน 500 แถว (`on_conflict=user_id,id`) เซิร์ฟเวอร์จะข้ามแถวที่เก่ากว่าของที่มีอยู่เองเงียบๆ · ถ้าเซิร์ฟเวอร์ปฏิเสธบางแถว (ข้อมูลผิดรูปแบบ, 4xx ที่ไม่ใช่ 401/403/404/429) แอปจะแบ่งครึ่งส่งใหม่จนเจอแถวเสีย กันแถวนั้นไว้ในรายการ **"ส่งไม่ได้"** (แสดงจำนวนในการ์ดซิงก์) แล้วซิงก์รายการอื่นต่อ — แก้รายการนั้นแล้วจะลองส่งใหม่เอง
- **ดึง (pull):** push ก่อนแล้วค่อยดึงแถวที่เซิร์ฟเวอร์เปลี่ยนหลังจุดที่จำไว้ (cursor) ครั้งละ 1000 แถวจนหมด (แบ่งหน้าแบบ keyset ด้วย `(server_updated_at, id)` ไม่ใช้ offset จึงไม่ตกหล่นแม้อีกเครื่องแก้ข้อมูลระหว่างดึง) ใช้ฉบับจากเซิร์ฟเวอร์ก็ต่อเมื่อ `client_updated_at` ใหม่กว่าในเครื่อง การรวมไม่แตะ `updated_at` และไม่ทำให้รายการกลับไปเป็น "รอส่ง" จึงไม่วนซ้ำ และรวมซ้ำกี่รอบก็ได้ผลเท่าเดิม
- **ลบ:** เป็น soft delete (`deleted = true` แล้วซิงก์เหมือนการแก้ปกติ) เครื่องอื่นจะเห็นว่าถูกลบ · ลบที่ใหม่กว่าการแก้ → ลบชนะ, แก้ที่ใหม่กว่าการลบ → แก้ชนะ
- **ออฟไลน์:** จดได้ตามปกติ รายการเก็บเป็น "รอส่ง" แล้วส่งเองเมื่อกลับมาออนไลน์
- **token หมดอายุ:** ต่ออายุอัตโนมัติก่อนหมดหรือเมื่อเซิร์ฟเวอร์ตอบ 401 ถ้าต่ออายุไม่ได้ (ไม่ได้เปิดแอปนานมากหรือเปลี่ยนรหัสผ่าน) จะขอให้ล็อกอินใหม่ ข้อมูลที่รอส่งไม่หาย

## ข้อจำกัดของรอบแรก

- ยังไม่มีหน้าจอใช้เทมเพลตโปรแกรม (ข้อมูลเก็บไว้แล้ว)
- ซิงก์แก้ขัดแย้งรายเรคคอร์ด (ฉบับที่แก้ทีหลังชนะ) ไม่รวมรายฟิลด์
- ยังไม่มีตัวจับเวลาพัก
- ท่า Plank (วัดเป็นวินาที) ใช้ช่อง "ครั้ง" เป็นวินาที และไม่คำนวณ 1RM
- ท่าที่ใช้เครื่องช่วย (assisted pull-up) ยังไม่รองรับน้ำหนักติดลบ ให้จดน้ำหนักที่ช่วยในหมายเหตุ
- ความเป็นส่วนตัว: โค้ดบน GitHub Pages ไม่มีข้อมูลของใคร ข้อมูลอยู่ในเบราว์เซอร์ของแต่ละเครื่อง (และบน Supabase ของคุณถ้าล็อกอินซิงก์) อย่าอัปโหลดไฟล์สำรองหรือ `private/` ขึ้นที่สาธารณะ
- `window.__app` เปิดไว้ให้ดีบัก/ทดสอบในคอนโซล (อ่านข้อมูลของเครื่องตัวเองเท่านั้น)
